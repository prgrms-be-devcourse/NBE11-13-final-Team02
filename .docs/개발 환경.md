# 개발 환경

처음 받은 팀원이 로컬에서 돌리고 PR을 올리기까지 필요한 내용이에요.

## 준비물
- JDK 25, Python 3.12, [uv](https://docs.astral.sh/uv/), Docker Desktop

## 로컬 인프라
```bash
cp infra/.env.example infra/.env     # 로컬 기본값이 들어 있어요. 필요하면 값만 바꿔요
docker compose -f infra/docker-compose.yml --env-file infra/.env up -d postgres rabbitmq
docker compose -f infra/docker-compose.yml down       # 끄기 (데이터는 볼륨에 남아요)
```

| 서비스 | 주소 | 비고 |
| --- | --- | --- |
| PostgreSQL + PostGIS | `localhost:5432` | DB `api`·`collector`·`extraction`, 사용자 `api_app`·`collector_app`·`extraction_app` |
| RabbitMQ | `localhost:5672`, 관리 화면 http://localhost:15672 | 계정은 `.env`의 `RABBITMQ_USER`·`RABBITMQ_PASSWORD` |

- DB와 사용자는 `infra/db/init/01-databases.sh`가 **볼륨이 비어 있을 때 한 번만** 만들어요. 스크립트를 바꿨다면 `down -v`로 볼륨을 지우고 다시 띄워야 반영돼요.
- 5432 포트를 다른 PostgreSQL(Homebrew 등)이 쓰고 있으면, 앱이 그쪽에 붙어서 엉뚱한 오류가 나요. `lsof -nP -iTCP:5432 -sTCP:LISTEN`으로 먼저 확인해요.

## api
```bash
cd services/api
./gradlew bootRun                                  # 실행 (위 인프라가 떠 있어야 해요)
./gradlew spotlessApply check                      # 포맷 맞추기 + 전체 검사 (커밋 전)
./gradlew test --tests '*ModuleStructureTest'      # 모듈 경계 검사만
```

### Docker가 필요한 명령
| 명령 | Docker 필요 |
| --- | --- |
| `compileJava`, `bootJar`, `build -x test` | 아니요 |
| `test --tests '*ModuleStructureTest'` | 아니요 |
| `test`, `check`, `build` | **예**. `ApiApplicationTests`가 Testcontainers로 PostGIS 컨테이너를 띄워요 |
| `bootRun` | DB가 필요해요. 보통 위 compose로 띄워요 |

- DB가 필요한 테스트는 `@Import(TestcontainersConfiguration.class)`를 붙여요.
- 커버리지 리포트는 `build/reports/jacoco/test/html/index.html`에 생겨요.
- 측정 대상은 각 모듈 `service` 패키지와 `eligibility/rule`이고, 라인 80% 미만이면 `check`가 실패해요.

## 파이썬 (collector · extraction)
```bash
cd services/<collector|extraction>
uv run ruff check && uv run ruff format --check && uv run pytest
```
ruff 설정은 루트 `ruff.toml`에 있어요(줄 길이 120, Python 3.12).

## 브랜치와 PR
- 흐름은 `기능 브랜치 → dev → main`이에요. 자세한 이유는 [브랜치 흐름과 CI 기준](adr/브랜치-흐름과-CI-기준.md)에 있어요.
- 브랜치 이름: `유형/범위-설명` (예: `feat/collector-http-client`)
- 커밋·PR 제목: `유형(범위): 요약` (예: `Feat(collector): PoliteClient 추가`)
- 기능 브랜치는 `dev`에서 따요. PR 대상은 기본값 `dev` 그대로 두면 돼요. 머지는 squash예요.
- 배포할 때 `dev → main` PR을 열어요. 머지는 merge commit이에요.
- 머지하려면 아래 조건을 모두 채워야 해요.
  - **승인 1명.** 본인 PR은 본인이 승인할 수 없어서 팀원에게 받아야 해요.
  - 필수 체크 통과
- 머지한 브랜치는 자동으로 지워져요.

### 쌓인 PR (stacked PR)
큰 작업은 PR을 여러 개로 나눠 쌓아요. 예: `dev ← #1 ← #2 ← #3`
- 각 PR의 base는 바로 앞 PR의 브랜치예요. 그래서 PR 화면의 diff에는 그 단계의 변경만 보여요.
- PR 본문 맨 위에 `스택 2/6 · 이전 #N · 다음 #M`처럼 위치를 적어요.
- **리뷰와 머지는 아래(첫 PR)부터 차례로** 해요. 위 PR을 먼저 머지하면 아래 변경이 섞여 들어가요.
- 아래 PR이 dev에 squash로 머지되면 브랜치가 자동으로 지워져요. 이때 GitHub가 다음 PR의 base를 dev로 바꿔요.
  - 작성자는 다음 브랜치를 `git rebase --onto origin/dev <앞 브랜치의 옛 끝 커밋>`으로 옮겨요. 앞 단계의 옛 커밋을 빼려는 거예요.
  - 그다음 `git push --force-with-lease`로 올려요.
- 필수 체크는 PR이 dev를 향할 때 걸려요. 쌓인 상태에서도 CI는 돌지만, dev로 바뀐 뒤 다시 초록인지 확인하고 머지해요.

### CI 체크
| 체크 | 하는 일 |
| --- | --- |
| `api (spotless · test · 모듈 경계)` | `./gradlew check`. 실패하면 Actions 화면의 `api-reports`에서 테스트·커버리지 리포트를 받을 수 있어요 |
| `python (ruff)` | collector·extraction·python-platform 린트와 포맷 검사 |
| `main 머지는 dev에서만` | main 대상 PR만. 출발 브랜치가 `dev`가 아니면 실패 |

## 알려진 문제
- **MinIO**: Docker Hub와 quay.io 모두에서 `minio/minio`, `minio/mc` 이미지를 받을 수 없어요. compose에 정의는 남아 있지만 실행 명령에서 뺐어요.
  - collector는 원본 파일을 S3(로컬은 MinIO)에 저장해서, 받을 수 있는 MinIO 이미지로 바꿀 예정이에요.
  - 진행 상황은 [collector 진행 현황](collector/진행%20현황.md)의 3번 브랜치를 봐요.
